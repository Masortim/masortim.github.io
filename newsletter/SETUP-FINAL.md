# Финальная настройка рассылки

Эта инструкция — про последний шаг, который нельзя сделать из кода: подключить
отправку писем. Всё остальное уже работает и проверено на живом API:
подписка, подтверждение, отписка, запись в Supabase, CORS, защита выпуска.

Пока шаг не сделан, форма на сайте честно отвечает
«Адрес принят, но отправка писем ещё настраивается» — ничего не ломается.

---

## Что уже готово

| Часть | Адрес / значение |
| --- | --- |
| API рассылки | `https://masortim-newsletter.vercel.app` |
| Самодиагностика | `https://masortim-newsletter.vercel.app/api/newsletter/health` |
| Хранилище подписчиков | Supabase, таблица `public.newsletter_subscribers` |
| Выпуск по расписанию | Vercel Cron, воскресенье 09:00 UTC |
| Переменные в Vercel | `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `NEWSLETTER_SITE`, `NEWSLETTER_API_BASE`, `CRON_SECRET` |

Не хватает двух переменных: `RESEND_API_KEY` и `NEWSLETTER_FROM`.

---

## Шаг 1. Понять ограничение с адресом отправителя

Это главная причина, по которой «просто вставить ключ» не работает.

Resend отправляет письма **только с домена, который вы добавили в свой аккаунт
и подтвердили DNS-записями**. Адрес отправителя должен быть на этом домене.
Поддомены проверяются отдельно: подтверждение `example.com` не подтверждает
`mail.example.com`.

Сайт живёт на `masortim.github.io`. Это домен GitHub: добавить туда DNS-записи
нельзя, поэтому `digest@masortim.github.io` Resend отклонит всегда — сколько бы
ключей ни выпускали.

Отсюда два пути: **свой домен** (правильный) или **тестовый адрес** (проверить
цикл, но письма будут уходить только вам).

## Что уже сделано за вас

- `NEWSLETTER_FROM = Masortim <onboarding@resend.dev>` задан в Vercel.
- `RESEND_API_KEY` задан в Vercel (Production, Preview, Development).
- Прод перевыпущен после добавления ключа, `/api/newsletter/health` отвечает.
- Самодиагностика понимает тестовый режим: `resend.dev` не требует проверки домена.
- Проба в Actions после появления ключа прогонит подписку, подтверждение, отписку
  и проверит, что строка удалена (нужны секреты репозитория — см. шаг 9).
- Отписка удаляет адрес из базы, а не помечает его: пробный адрес можно
  использовать повторно, и в таблице не копятся отписавшиеся.

Настройка серверной части закончена. Остались два действия в панели GitHub —
их не может сделать ни один агент (у интеграции нет прав на секреты репозитория):

1. **Settings → Secrets and variables → Actions** → добавить `NEWSLETTER_OWNER_EMAIL`
   со значением `alex.typeface@gmail.com`.
2. Туда же — `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` (значения из шага 4).

После этого проба сама прогонит подписку → подтверждение → отписку и проверит,
что строка удалена. Без секретов она проверяет только то, что видно снаружи,
и пишет «пропущено», а не краснеет.

## Шаг 2. Путь А: свой домен (рекомендуется)

Нужен любой домен, которым вы владеете, и доступ к его DNS. Домен не обязан
быть связан с сайтом: рассылку можно вести с `updates.<домен>`.

1. **Купите или возьмите домен.** Подойдёт дешёвый в любой зоне; важны только
   DNS-записи. Бесплатные варианты:
   - Cloudflare Registrar — по себестоимости, DNS уже под рукой;
   - Namecheap / Porkbun — первый год часто со скидкой;
   - если домен уже есть под другие задачи — используйте поддомен
     `updates.<домен>`, чтобы репутация рассылки не смешивалась с почтой.

2. **Добавьте домен в Resend.** [resend.com/domains](https://resend.com/domains)
   → **Add Domain** → впишите `updates.<домен>` (именно поддомен, так советует
   сам Resend: проще изолировать рассылку). Регион — ближайший, например
   `eu-west-1` или `us-east-1`.

3. **Скопируйте DNS-записи.** Resend покажет три записи: `MX` и `TXT` (SPF) на
   поддомене рассылки и `TXT` (DKIM) на `resend._domainkey.updates`.

4. **Внесите их у DNS-провайдера.** Частые ошибки:
   - в поле «Name» нужен только префикс (`send`, `resend._domainkey`), сам
     домен панель добавит автоматически;
   - если у домена уже есть SPF-запись, **не создавайте вторую** — в SPF
     должна быть одна запись, включите в неё `include:amazonses.com`;
   - на Cloudflare CNAME-записи должны быть **DNS only** (серая тучка), иначе
     проверка не пройдёт.

5. **Дождитесь статуса `verified`.** Обычно 5–15 минут, иногда до 72 часов.
   Кнопка **Verify DNS Records** на странице домена запускает перепроверку.
   Статус `verified` — единственный, при котором можно отправлять.

6. **Создайте ключ.** [resend.com/api-keys](https://resend.com/api-keys) →
   **Create API Key** → Permissions: **Sending access** → Domain: ваш
   `updates.<домен>`. Скопируйте значение `re_…` — оно показывается один раз.

7. **Пропишите переменные в Vercel** (шаг 3 ниже):
   - `RESEND_API_KEY` = `re_…`
   - `NEWSLETTER_FROM` = `Masortim <digest@updates.<домен>>`

## Шаг 3. Путь Б: без домена (выбран сейчас)

Это текущий режим: `NEWSLETTER_FROM` уже равен `Masortim <onboarding@resend.dev>`.
Осталось только добавить ключ.

1. Зарегистрируйтесь на [resend.com](https://resend.com) — **тем же адресом**,
   на который хотите получать письма (`alex.typeface@gmail.com`). Письма с
   `onboarding@resend.dev` уходят **только владельцу аккаунта Resend**.
2. Подтвердите регистрацию по ссылке из письма Resend.
3. **API Keys** → **Create API Key** → Permissions: **Sending access**.
4. Скопируйте `re_…` (показывается один раз).

Больше ничего делать не нужно: `NEWSLETTER_FROM` уже задан, а `health`
распознаёт этот режим и не считает домен неподтверждённым.

**Ограничение режима:** письма приходят только на ваш адрес. На любой другой
Resend ответит `403 validation_error`, и форма покажет ошибку отправки. Когда
появится домен — поменяйте `NEWSLETTER_FROM` на адрес с него, код трогать не
нужно.

## Шаг 4. Переменные в Vercel

Оба пути заканчиваются здесь.

**Через панель:** Vercel → проект `masortim-newsletter` → **Settings** →
**Environment Variables** → **Add**:

| Key | Value | Environments | Состояние |
| --- | --- | --- | --- |
| `RESEND_API_KEY` | `re_…` | Production, Preview, Development | **нужен** |
| `NEWSLETTER_FROM` | `Masortim <onboarding@resend.dev>` | Production, Preview, Development | **уже задан** |

Для пути А (свой домен) `NEWSLETTER_FROM` меняется на адрес с него.

**Через CLI** (из корня репозитория):

```bash
vercel env add RESEND_API_KEY production
vercel env add NEWSLETTER_FROM production
```

Переменные применяются только к **новым** деплоям: изменение переменной не
перезапускает уже собранную функцию.

---

## Шаг 5. Перевыпустить деплой

Переменные окружения применяются только к **новым** деплоям, поэтому после
шага 4 нужен новый.

**Панель:** Vercel → проект `masortim-newsletter` → **Deployments** → у верхнего
деплоя ⋯ → **Redeploy**.

**CLI:**

```bash
cd newsletter
npm run build      # пересобрать newsletter/edge/index.mjs из исходников
git add newsletter/edge/index.mjs && git commit -m "newsletter: пересборка"
git push
vercel --prod      # если деплоите вручную, а не из git
```

Сборка обязательна: Vercel разворачивает **готовый** `newsletter/edge/index.mjs`
(каталог проекта — `newsletter/edge`), а не исходники из `api/` и
`newsletter/lib/`. Файл лежит в git именно для этого.

Проверка, что выкатилось именно то:

```bash
curl -s https://masortim-newsletter.vercel.app/ | head -20
```

В ответе — `{"name":"masortim-newsletter","endpoints":[...]}`. Если вместо
этого `No entrypoint found` в логах деплоя, значит из сборки выпал
`newsletter/edge/index.mjs` — пересоберите (шаг 5) и повторите.

## Шаг 6. Проверить самодиагностику

Откройте в браузере:

```
https://masortim-newsletter.vercel.app/api/newsletter/health
```

Что должно быть в ответе:

```json
{
  "ready": true,
  "blocking": [],
  "checks": {
    "resendKey": true,
    "fromSet": true,
    "senderDomain": "updates.ваш-домен",
    "fromDomainStatus": "verified",
    "fromDomainVerified": true,
    "resendDomains": ["updates.ваш-домен (verified)"]
  }
}
```

`ready: true` — можно отправлять. Если `false`, массив `blocking` содержит
ровно то, что осталось; расшифровка:

| Ответ | Что означает |
| --- | --- |
| `resendKey: false` | переменная не задана или деплой не перевыпущен |
| `senderDomain` = `masortim.github.io` | домен GitHub, Resend его не примет — нужен свой |
| `fromDomainStatus: "pending"` | DNS-записи внесены, но Resend их ещё не увидел |
| `fromDomainStatus: null` | такого домена нет в вашем аккаунте Resend |
| `fromDomainStatus: "failed"` | записи не совпали; сверьте и нажмите Verify DNS Records |

Эндпоинт секретов не раскрывает: только «задано / не задано» и статусы.

## Шаг 7. Проверить весь цикл

1. Откройте `https://masortim.github.io/newsletter/` и подпишитесь **своего**
   адреса (для пути Б — того, на который зарегистрирован Resend).
2. В течение минуты приходит письмо «Подтвердите подписку». Нажмите кнопку.
3. Откроется страница сайта с сообщением об успехе и придёт второе письмо.
4. В Supabase (Table Editor → `newsletter_subscribers`) у строки статус
   `confirmed`.
5. Внизу письма нажмите «Отписаться» — **строка исчезнет из таблицы**.
   Отписка удаляет адрес, а не помечает его: тот, кого попросили забыть,
   в базе не остаётся.

Если письмо не приходит — смотрите **Vercel → Deployments → Functions → Logs**:
там видно точный ответ Resend (`403`, `validation_error`,
`domain is not verified` и т. п.).

## Шаг 8. Проверить выпуск, ничего не отправляя

```bash
curl -s -H "Authorization: Bearer $CRON_SECRET" \
  "https://masortim-newsletter.vercel.app/api/newsletter/digest?dry_run=1"
```

Ответ содержит записи, которые попадут в выпуск, и список получателей —
писем при этом не отправляется. `CRON_SECRET` лежит в переменных Vercel.

Без секрета тот же адрес отвечает `401` — это правильно, выпуск не должен
быть доступен всем.

## Шаг 9. Проверка снаружи (без вашего участия)

В репозитории есть проба, которая прозванивает живой API так же, как это
сделал бы браузер читателя:

```bash
gh workflow run newsletter-probe.yml
gh run list --workflow=newsletter-probe.yml --limit 1
```

Она проверяет: корень, отказ на битом адресе, приём валидного, защиту выпуска,
CORS для `https://masortim.github.io`, отсутствие Vercel Authentication,
самодиагностику и `newsletter/config.js` на сайте.

После настройки ключа в логе шага **Self-diagnosis says what is missing**
должно быть `HEALTH ready=true`, а шаг **Full flow** пройдёт весь цикл.

Чтобы цикл проходил автоматически, добавьте в **Settings → Secrets and variables
→ Actions** два секрета:

| Имя | Значение |
| --- | --- |
| `NEWSLETTER_OWNER_EMAIL` | адрес владельца аккаунта Resend — единственный, куда доходят письма в тестовом режиме |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | те же значения, что в переменных Vercel (шаг 4) — по ним проба читает токен подтверждения и проверяет удаление строки |

Без `NEWSLETTER_OWNER_EMAIL` проба не может отправить письмо (тестовый режим
принимает только адрес владельца), поэтому шаг честно скажет «пропущено»,
а не покраснеет. Без `SUPABASE_*` она проверит подписку и защиту выпуска, но не
пройдёт по ссылкам подтверждения и отписки.

## Что стоит знать заранее

- **Лимиты бесплатного плана Resend:** 3000 писем в месяц, не больше 100 в
  день, 3 домена. Для дневника с десятками подписчиков — с запасом.
- **Письма уходят с `NEWSLETTER_FROM`.** Имя и адрес можно менять свободно,
  домен — только на подтверждённый.
- **Supabase на бесплатном плане засыпает после недели простоя.** Первый
  запрос после паузы может ответить ошибкой; повторный обычно проходит.
- **Двойная подписка (double opt-in).** Адрес попадает в список только после
  клика в письме, поэтому опечатка не создаёт «мёртвого» подписчика.
- **Язык письма** берётся из языка сайта, на котором человек подписался;
  переключатель в письме не нужен.

## Если что-то не сходится

| Симптом | Причина и что делать |
| --- | --- |
| Форма: «Адрес принят, но отправка писем ещё настраивается» | нет `RESEND_API_KEY` — шаг 4 и перевыпуск деплоя |
| `502 email_failed`, в логах `403 validation_error` | адрес отправителя на неподтверждённом домене — шаги 2–3 |
| `onboarding@resend.dev` не доставляет | так и задумано: только на адрес владельца аккаунта |
| `health` показывает `senderDomain: masortim.github.io` | `NEWSLETTER_FROM` не задан, работает значение по умолчанию |
| Письмо подтверждения не пришло, в логах `200` | проверьте «Спам» и адрес: Resend отправил, дальше решает почтовый провайдер |
| В логах деплоя `No entrypoint found` | в сборке нет `newsletter/edge/index.mjs` — `npm run build`, коммит, новый деплой |
